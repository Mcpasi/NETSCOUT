# Local content relevance assessment

NetScout separates **candidate retrieval** from **assessment of topic relevance**. Platforms still return keyword candidates. Simply finding the words somewhere in a whole post is insufficient.

1. Individual connected original sentences/passages of up to 700 characters are selected from the returned text. Two neighboring sentences in the same paragraph are also checked when evidence is distributed. Together, the title and passage must support all entered keywords. Selection also examines occurrences beyond the first 100 mentions. Complete matching windows retain context without cutting off required terms. Passages with more keyword evidence take precedence over generic introductions, even when the title already contains every term. Separate list entries, release-note sections, or distant mentions are not artificially joined into a preview.
2. A multilingual **cross-encoder** reads the query alongside each selected passage. It produces a learned relevance score rather than a word count. At most four passages per candidate and four pairs per model call are assessed, with a maximum of 384 tokens per pair, including up to 96 query tokens. A negative model assessment rejects the candidate.
3. The highest model score determines relevance sorting. Platform rank is only a small tie-breaker. For newest sorting, publication date remains the primary ordering, while content assessment still applies. The preview displays the exact assessed original passage; it is neither generated nor a model explanation.

When there is no complete local sentence-level match, only the semantic assessment additionally receives up to four **unchanged original excerpts of up to 1,000 characters**. This helps when, for example, a project introduction names the agent and a following platform paragraph mentions Android. All keywords must still be supported by the title and excerpt. Up to four required sentence/paragraph parts are checked for continuity with the first piece of evidence: an immediate personal back-reference (`It`, `Es`, `Er`, `Sie`) can continue the previous subject, without skipping intervening text. Otherwise, the model assesses the two parts in both query/passage directions. The higher raw score must reach at least −5, in addition to the normal nonnegative query/passage score. This empirical continuity threshold is not a probability either. Tests include relevant paragraphs about different topics and unrelated release notes whose combined keyword text alone receives a high model score. The deterministic core implementation without the model does not extend its paragraph boundary.

## Model and distribution

- Model: [Horizon-Labs/multilingual-reranker-small](https://huggingface.co/Horizon-Labs/multilingual-reranker-small/tree/d35a2781eeb3de1d971ad328165277bdf5712e35), v1.2, a 141M-parameter mmBERT-small cross-encoder supporting 40+ languages. This is the **Small** reranker. The former mMARCO MiniLM model is no longer bundled.
- Immutable revision: `d35a2781eeb3de1d971ad328165277bdf5712e35` (2026-10-20 release).
- Quantized ONNX model, `onnx/model_quantized.onnx`, 268,407,694 bytes. The upstream quantization applies int8 to embeddings, leaving computation weights in float32. The identical model is used on Android, JVM and the x86_64 emulator; no export or quantization tools run during builds.
- Model SHA-256: `f913154682468bfe92d6a7e02ed4e994e548c112fddc74452b573b17c949046e`.
- Source tokenizer: `tokenizer.json`, 34,363,439 bytes, SHA-256 `7925f638b5444897efe3b4608eed56c1652f0ed39c2662c8302de1bc264c6088`.
- Model license: Apache-2.0; see the [license text](../third-party/APACHE-2.0.txt).
- Runtime: Microsoft ONNX Runtime 1.23.2, [MIT license](../third-party/ONNX-RUNTIME-LICENSE.txt), also included in the APK. The Android AAR contains the native libraries.
- `BpeTokenizer` implements the original mmBERT/Gemma BPE tables: literal ASCII spaces become `▁`, metaspace splits retain their separators, and ranked merges use UTF-8 byte fallback for unknown characters. Added tokens (including newlines and repeated tabs) are matched before ordinary tokenization. It preserves the original normalization behavior; it does not apply the former SentencePiece normalization or collapse arbitrary whitespace.
- Pairs use `<bos> query <eos> passage <eos>` (IDs `2 … 1 … 1`), right padding uses ID `0` with attention mask `0`, and each pair has at most 384 tokens including up to 96 query tokens and three special tokens. The scorer returns the single raw `logits` value per pair without sigmoid or softmax.
- The build compiles only the alphabet, byte IDs, added tokens and ranked merge tables into the documented `NSBP1` format in `scripts/prepare-relevance-model.py`. Merge lookups use sorted primitive arrays to keep the Android Java heap small. The compiled tokenizer is 9,462,546 bytes, SHA-256 `cb744a8fb04393ba0d46dc8e51fc0118d1b879439a6720e57551a5cb412f1c95`; preparation and release verification check it against the lock file.

`scripts/prepare-relevance-model.py` verifies size and SHA-256 from `relevance-model.lock.json` and packages the model, tokenizer, model lock, documentation and license into the APK. For local debug builds, missing downloads are cached under `~/.cache/netscout-models`; GitHub Actions debug and device jobs use the same verified cache. For F-Droid and the release job, `--download-only --cache-dir .model-cache` downloads inputs in advance. This phase does not yet generate a binary tokenizer. The Gradle build uses `-Pnetscout.modelCache=.model-cache -Pnetscout.offlineModel=true`: missing or modified files fail the build without attempting network access. Gradle's `--offline` also switches model preparation to offline mode. There are no runtime downloads or model changes through a moving `main` branch. The weights are licensed data; they are not retrained in this project.

On Android, the uncompressed model asset is memory-mapped rather than copied into another file. Native runtime libraries are compressed in the APK and extracted during installation only for the matching CPU. One model per process, two CPU threads, and small batches limit resource use. Initial model loading and every result page take additional processing time, especially on older devices. The model and runtime substantially increase APK size. Search texts and assessments stay on the device; selected search platforms receive the keywords as before. A model failure produces a visible source error rather than silently reverting to a simple keyword-AND list.

The pinned weights and compiled tokenizer alone total approximately 278 MB before APK compression. The universal APK also includes runtimes for ARM64, ARMv7, x86 and x86_64. Compared with the previous 119 MB model, Horizon Small increases download size and memory requirements; no speed or device-wide quality improvement is assumed from the model name. Actual build sizes and checks are recorded in [0.4.0 changes](changes-0.4.0.md).

## Interpretation and limits

This is a local semantic **reranker**, rather than a complete semantic search over platform indexes. By default candidate queries remain literal. The optional term-expansion switch adds at most two explicit dictionary-based queries per source, as documented in [0.3.8 changes](changes-0.3.8.md); the model itself does not rewrite queries or translate them. The model cannot find results a platform does not return or text it does not provide. Limited text windows, four passages per candidate, and conservative continuity checks can miss other relevant connections. Paragraph comparisons require additional model calls when local sentence checking finds no evidence.

A relevance score is **not a calibrated probability** or proof of a logical relationship. Quantized raw scores also vary with CPU kernels and padding/batch composition; tests therefore check ordering and acceptance rather than identical floating-point values. The zero cutoff is a simple exclusion threshold; further quality work needs diverse human-labeled search examples. Short ambiguous queries can have multiple meanings even for a model. Proper names, negation, lists within a sentence, and new technical terms can cause misclassification. NetScout claims neither perfect results nor guaranteed language understanding. Independent passage checking is particularly useful for long compilation posts, where older retrieval models can overvalue isolated mentions.

JVM tests use the real quantized model, fixed tokenizer reference vectors, and additional arbitrary search topics. An Android device test loads the same asset through the production path. Mock tests cover errors, cancellation, filtering, and pagination without external platform requests.
