# NetScout architecture

## Responsibilities

`app` contains the Compose UI, a screen-wide `SearchViewModel`, and `SettingsStore`. Android dependencies exist only here. The `StateFlow` UI displays partial results and keeps filter edits separate from the active search request. A new search or changed credentials cancel older requests; old results cannot overwrite a new search.

`app/favorites` encapsulates favorites independently of search requests and credentials. `Favorite` stores a display snapshot with the original link, passage, source metadata, and keywords for highlighting; the longer provider text stays in memory. `FavoritesRepository` maintains observable state, serializes changes with a coroutine mutex, identifies entries using the same canonical URL as search, and enforces the limit of 20 without automatic eviction. The UI updates only after a successful save. Failed reads block changes until a successful reload, preventing existing data from being overwritten.

`FavoritesStore` separates these rules from the Android filesystem. `FileFavoritesStore` uses `AtomicFile` in the private app directory and performs reads and writes on `Dispatchers.IO`; `FavoritesCodec` defines the versioned JSON format. Incomplete writes preserve the previous state. Data is excluded from backups and device transfers and remains until removal, clearing app data, or uninstallation. `FavoritesViewModel` survives screen rotation; `FavoritesScreen` and search share the same `ResultCard` with an accessible star toggle. The favorites screen is accessible without a search request, preserves search state, and supports Android's back button.

`core:search` defines `SearchRequest`, `SearchItem`, `SearchCursor`, `SourcePage`, `SourceOutcome`, `SearchProvider`, and the independent `SearchRelevance` interface. `KeywordQuery` parses arbitrary comma/semicolon/space separators and quoted phrases, creates literal provider queries, checks Unicode word boundaries, and locates highlighting spans. `PassageSelector` finds individual connected original passages rather than aggregating keywords across a whole post. `ContextRelevance` is the deterministic library implementation; the Android application additionally injects the semantic model. The merger respects assessment and handles date/URL checks, merging, and sorting. Neither platform rank nor newest sorting can override a model rejection.

The engine emits sources independently as a Flow, after assessing each page's content. A separate `SourceProgress` callback reports `FETCHING` and `ASSESSING` with loaded candidate counts, without releasing unchecked results. The UI tracks running sources separately from their last completed pages, keeping pagination visibly active. Cancellation and a new search generation remove old progress information. Successfully assessed pages are cached in memory for 60 seconds, with a limit of 64 entries. Errors are not cached; failed assessment never releases an unchecked result list. Each platform request has an 18-second timeout, followed by a separate 60-second assessment timeout. Collection cancellation propagates to providers and assessment. Model inference checks for cancellation between small batches; a native batch already running completes first.

`SearchItem.searchText` contains the returned text before truncation, including paragraph/list boundaries. `assessment` holds acceptance, the model ranking score, and the original passage; `snippet` displays that exact passage. Author names, source names, and tracking URLs cannot justify a match on their own. The UI uses the active query for highlighting, counts only accepted matches per source, and shows excluded candidate counts. Pagination remains possible after a page is entirely rejected.

`data:relevance` encapsulates the pinned Horizon Small multilingual ONNX cross-encoder and its mmBERT BPE tokenizer with original merge ranks, added tokens, byte fallback and pair template. `SemanticRelevance` connects passage checking with a replaceable `PassageScorer`. The large runtime is `compileOnly` in the library; Android uses the Android AAR, while JVM tests use the desktop runtime. `app/LocalSemanticSearch` is the only Android-specific asset loader: memory mapping, one model per process, and lazy loading on the first assessable search. Settings changes and new searches do not create additional model sessions. The build downloads verified, revision-pinned files and packages them with their license; the device needs no model server. Details and limits: [relevance-model.md](relevance-model.md).

`data:search` encapsulates OkHttp and all platform details. The transport sets connection, read, and call timeouts, limits responses to 2 MiB, cancels HTTP calls on coroutine cancellation, and retries temporary network/5xx errors once. Rate limits cause a pause based on `Retry-After`/`X-RateLimit-Reset`; Stack Exchange `backoff` is also respected. There are no automatic HTTP redirects, HTTP logs, or disk cache.

## Adding providers

1. Add a `SearchSource` with a clear label and setup guidance.
2. Implement `SearchProvider` in the data module. Register exactly one instance per platform. Results must supply original URLs, a stable identifier, and the global rank across all pages.
3. Set a date only when it is a publication/creation date. Pass missing dates as `null`; never substitute the current time.
4. Return the backend cursor and cumulative rank offset as `SearchCursor`. Return `nextCursor = null` at the end. Respect platform limits; do not automatically fetch every page.
5. Provide user-readable errors through `SourceException`. Do not include raw responses, tokens, or request URLs in error messages.
6. Register the provider in `ProviderFactory` and add HTTP fixtures for queries, dates, paging, and error handling.

Direct and index cursors are separate. Fallback cursors internally carry an `index:` prefix per fallback stage; each adapter removes exactly one stage. A page-2 failure does not silently switch backend cursors. On the first page, the primary adapter gets four seconds, so a stalled API/search endpoint cannot block fallback until the whole engine timeout expires. External cancellation propagates.

`PublicWebProvider` uses public Brave HTML results and DuckDuckGo HTML as its second service. `SearchIndexScope` generates appropriate site queries and independently validates result hosts/paths. Ads, navigation, and unrelated answer cards are not used as evidence. Brave cursors contain only the returned page offset; DuckDuckGo cursors contain permitted form fields. Continuations always request the fixed service with unchanged keywords, never an arbitrary cursor URL. The app imposes no fixed page/daily quota on public search. CAPTCHA pages cause a visible pause and a ten-minute host cooldown; unknown HTML is an error rather than an empty result list. The shared HTTP transport retains size limits, cancellation, TLS verification, and the absence of logs/disk cache.

`ProviderFactory` enables all six sources with entirely empty `ApiSettings`. GitHub/HN/Forums first try public APIs. YouTube/Reddit use the index directly without optional credentials. Configured SearXNG is preferred before the public index. Optional API keys stay restricted to their respective API; fallback never receives them.

## Deliberate limits and next steps

- Public web search is free and needs no configuration, but services can change layout, coverage, continuations, and blocks. The app does not cycle through random public SearXNG instances. A personal/permitted instance remains optional.
- Without a token, Reddit search uses publicly indexed discussions. Full direct API access still requires approval/OAuth; optional tokens must be renewed manually. No client secret is hidden in the APK.
- Without an API key, YouTube search uses publicly indexed videos. A personal Data API key remains optional for more precise data. Indexed passages do not replace complete descriptions/transcripts; dates are accepted only when explicitly identified as publication dates.
- GitHub searches repository names/descriptions and issue/PR titles/bodies in three separate requests. GitHub App user tokens are supported. README, code, and Discussions need separate adapters; complete README files are not fetched for each repository, conserving anonymous quotas.
- A failed GitHub subrequest is reported; the next page may skip results from that part, similarly to forum batches. With newest sorting, repository candidates are fetched by API update time, then centrally sorted by the creation dates of loaded results.
- Forums covers three Stack Exchange sites, including index fallback. Additional Discourse/forum adapters can follow. UI guidance stays as specific as the actual coverage.
- A forum batch can skip a site's results on a page if that site fails; the source notice reports the partial failure. A future cursor per subadapter would improve targeted retries.
- Candidate retrieval is literal by default, with the optional bounded dictionary expansion described below; final sorting uses semantic query/passage scores and a very small RRF tie-breaker. The model does not generate translations or synonyms. Local passage/title evidence considers two neighboring sentences up to 700 characters and four selected passages per candidate. When local evidence is missing, `semanticCandidates` adds unchanged windows of up to 1,000 characters with the necessary context parts. `SemanticRelevance` additionally requires an immediate back-reference or model evidence connecting those parts; the core-only check stays conservative. Other relationships may be missed. Models can misclassify even with textual evidence, especially with ambiguous proper names and lists within a sentence. Raw-logit thresholds are not calibrated quality guarantees; varied human-labeled search tasks are a next step. GitHub/HN have no language restriction; SearXNG uses `language=all`. Keyword language and varying model quality by language influence the actual language mix.
- Results remain in memory unless explicitly saved as one of up to 20 favorites. Full-text offline search, search history, synchronization, and background jobs are separate future features.
- App text is currently German. Move it into Android string resources before adding more localizations.

## Verification

Favorites tests cover restoration after new repository/store/ViewModel instances, permanent removal, capacity including freeing a slot, concurrent changes, canonical URL identity, and read/write errors. Codec tests cover Unicode, metadata, highlighting queries, invalid formats, and missing fields. Android file tests simulate an interrupted atomic write. Compose tests operate stars in search and favorites, check the empty state, reopening after restart without another search, and the notice for a 21st favorite.

JVM tests cover inclusive UTC date bounds, validation, comma/Unicode-space input, phrases, word boundaries, international text, neighboring sentences, complete long matching windows, source selection, URL deduplication, ranking, caching, timeouts, and cancellation during assessment. Separate list entries containing all query terms must not count as a relationship. Model tests cover original tokenizer reference vectors, real quantized inference in several languages, other arbitrary search topics, passage selection, and visible errors on model failure. MockWebServer tests cover HTTP requests/responses for every adapter, credentials, pagination, rate limits, retries, and partial errors. Compose/ViewModel tests cover accepted matches, counters, source phases, and rejected candidates, including scattered mentions. The optional `:data:search:checkLiveSearch` task checks real GitHub/HN/Forums results through the same model. The Keystore test checks encrypted Android persistence; another device test loads and uses the real packaged model. The debug workflow also verifies the finished APK's certificate and launches the packaged app.
